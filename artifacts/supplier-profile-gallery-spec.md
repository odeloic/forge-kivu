# Supplier Profile and Gallery Extension

Status: agreed design; implementation has not started.

## Goal

Extend supplier profiles with simple contact and presentation information, plus an ordered image gallery. Keep version one intentionally small and avoid turning gallery entries into project entities.

## Existing model

The current `suppliers` table already contains:

- `id`
- `name`
- `slug`
- `description`
- `logo_media_id`
- `visible`
- `created_at`

The existing media module owns uploaded files, tracks upload readiness, and resolves public URLs. Supplier images should continue to reference that shared media model.

## Agreed decisions

### Supplier profile

Add these nullable fields to `suppliers`:

- `email`
- `phone`
- `website_url`
- `address`
- `featured_media_id`

The logo, description, contact details, and featured image are single-value profile attributes and belong on the supplier record.

All new fields remain optional in version one, including for visible suppliers. Publishing completeness rules are deferred.

Version one supports one email, one phone number, one website, and one address per supplier. Multiple contacts and locations are deferred.

### Supplier gallery

Create a separate `supplier_gallery_items` table. Each row represents exactly one image belonging to exactly one supplier.

Proposed fields:

| Field | Shape | Notes |
| --- | --- | --- |
| `id` | UUID, primary key | Generated by the database |
| `supplier_id` | UUID, required | References `suppliers.id` |
| `media_id` | UUID, required | References `media.id` |
| `caption` | Text, nullable | Optional presentation copy |
| `alt_text` | Text, required | Accessibility text for the image |
| `link_url` | Text, nullable | Optional destination when the image is activated |
| `display_order` | Integer, required | Controls client presentation order |
| `created_at` | Timestamp, required | Stable fallback ordering and audit information |

Use explicit columns rather than a JSON metadata field. This keeps validation, API contracts, and future migrations predictable.

Gallery items are images with metadata, not projects. A gallery item does not have its own project title, project description, or nested image collection.

## Inferred implementation details

The following details support the agreed behavior but were not individually specified during brainstorming.

### Address representation

Store `address` as one free-form text value in version one. Structured address components can be introduced later if search, mapping, shipping, or regional validation requires them.

### Ordering

When `display_order` is omitted while creating a gallery item, append the item after the supplier's current last item. The service can assign the next order value.

Return gallery items ordered by:

1. `display_order` ascending
2. `created_at` ascending
3. `id` ascending

The secondary keys make the result deterministic if two rows temporarily share an order during reordering. A uniqueness constraint on `(supplier_id, display_order)` is not required for version one because atomic list reordering is simpler when temporary duplicate positions are permitted.

### Media rules

- `featured_media_id` and gallery `media_id` must reference media in the ready state before they can be assigned.
- Resolve `featuredImageUrl` and gallery image URLs through the existing public-media URL logic.
- Restrict deletion of a media record while it is referenced by a supplier logo, featured image, or gallery item.
- Deleting a gallery item removes the relationship and metadata, not the underlying media object.
- Deleting a supplier cascades to its gallery rows. It does not automatically delete referenced media objects.

### Constraints and indexes

- Add a foreign key from `suppliers.featured_media_id` to `media.id`, using `ON DELETE SET NULL`, matching the existing logo behavior.
- Add a foreign key from `supplier_gallery_items.supplier_id` to `suppliers.id`, using `ON DELETE CASCADE`.
- Add a foreign key from `supplier_gallery_items.media_id` to `media.id`, using the repository's restrictive default deletion behavior.
- Index `(supplier_id, display_order)` for ordered gallery reads.
- Prevent the same media item from appearing twice in one supplier gallery with a unique constraint on `(supplier_id, media_id)`.

## Validation

Suggested version-one validation:

- `email`: optional; trim and validate as an email address.
- `phone`: optional; trim, reject an empty value, and otherwise keep formatting permissive.
- `website_url`: optional absolute `http` or `https` URL.
- `address`: optional trimmed text with a reasonable maximum length.
- `featured_media_id`: optional UUID referencing ready media.
- `caption`: optional trimmed text with a reasonable maximum length.
- `alt_text`: required, trimmed, non-empty text with a reasonable maximum length.
- `link_url`: optional absolute `http` or `https` URL.
- `display_order`: optional on creation; otherwise a non-negative integer.
- `media_id`: required UUID referencing ready image media.

Accept `null` to clear optional scalar fields and the featured image. Treat an omitted field as unchanged during a patch.

## API shape

Supplier detail responses should expose resolved image URLs while retaining media identifiers for admin editing.

```ts
type SupplierGalleryItem = {
  id: string
  mediaId: string
  imageUrl: string
  caption: string | null
  altText: string
  linkUrl: string | null
  displayOrder: number
  createdAt: string
}

type SupplierDetail = {
  id: string
  name: string
  slug: string
  description: string | null
  logoMediaId: string | null
  logoUrl: string | null
  featuredMediaId: string | null
  featuredImageUrl: string | null
  email: string | null
  phone: string | null
  websiteUrl: string | null
  address: string | null
  visible: boolean
  gallery: SupplierGalleryItem[]
  createdAt: string
}
```

Recommended admin operations:

- Update the single-value supplier profile through the existing supplier update operation.
- Add a gallery item.
- Update a gallery item's metadata and display order.
- Remove a gallery item.
- Reorder the complete gallery in one request when the UI supports drag-and-drop.

The public supplier detail response may include contact details, featured image, and ordered gallery. Admin list responses can remain lightweight; gallery data should be loaded for supplier detail editing rather than repeated for every supplier in a list.

## Lifecycle behavior

1. Upload and confirm media through the existing media flow.
2. Assign ready media as a featured image or create a gallery item referencing it.
3. Edit gallery metadata independently from the media file.
4. Reorder gallery items without recreating them.
5. Remove the gallery relationship without implicitly deleting the uploaded media.

## Testing considerations

- Create and update every optional supplier profile field.
- Clear optional fields with `null`.
- Reject malformed email and URL values.
- Reject non-ready or unknown featured and gallery media.
- Require non-empty alt text.
- Append gallery items in insertion order when no order is supplied.
- Return gallery items in deterministic display order.
- Update captions, alt text, links, and ordering.
- Prevent duplicate use of the same media within one supplier gallery.
- Allow the same media record to be referenced by different suppliers if desired by the shared media model.
- Cascade gallery-row deletion when a supplier is deleted.
- Do not delete the underlying media object when a gallery item is removed.
- Resolve logo, featured-image, and gallery URLs consistently.
- Preserve current hidden-versus-visible supplier behavior.

## Deferred ideas

- Multiple contacts or contact people
- Multiple supplier locations
- Structured postal addresses
- Social-media links
- Publishing completeness requirements
- Project or case-study entities
- Multiple images per project
- Arbitrary JSON metadata
- Image focal points, crops, or responsive variants
- Automatic deletion of unreferenced media
